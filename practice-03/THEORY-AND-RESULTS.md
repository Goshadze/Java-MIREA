# Практика 3 — конспект к защите

## Блок 1. Теория

### 1. Класс, объект и ссылка

Класс описывает поля и методы. Объект — экземпляр класса, созданный через `new`. В строке `Car car = new Car();` первое `Car` задаёт тип переменной, `new Car()` создаёт объект и вызывает его конструктор, а переменная `car` хранит ссылку на этот объект.

Например, у BMW и Tesla свои значения поля `year`. Вызов `car.setYear(2018)` меняет год только у объекта, на который ссылается `car`. Поле `year` объявлено как `private` в `Vehicle`, поэтому клиент работает с ним через `getYear()` и `setYear(...)`. Сокрытие полей за методами называют **инкапсуляцией**.

### 2. Наследование и абстрактный класс

У обычной машины и электромобиля есть модель, цвет, год и владелец. Эти данные и методы доступа объявлены один раз в `Vehicle`. Слово `extends` связывает классы:

```text
Vehicle
└── Car
    └── ElectricCar
```

`Car` наследует методы `Vehicle`, а `ElectricCar` наследует их через `Car`. Например, `electricCar.getYear()` вызывает метод, написанный в `Vehicle`. Поле `year` входит в состояние электромобиля, хотя напрямую обратиться к нему из `ElectricCar` нельзя из-за `private`.

`Vehicle` объявлен как `abstract`. Это общий класс, экземпляр которого напрямую создать нельзя. У него есть обычные методы с телом, например `getYear()`, и абстрактный метод без тела:

```java
public abstract String vehicleType();
```

Этот метод обещает результат типа `String`. Конкретный класс должен предоставить или унаследовать его реализацию. `Car` возвращает `"Car"`. `ElectricCar` мог бы унаследовать это поведение, но переопределяет метод, чтобы вернуть `"Electric Car"`. Аннотация `@Override` помогает компилятору проверить, что сигнатура совпадает с унаследованным методом.

### 3. Как конструкторы заполняют один объект

При вызове `new ElectricCar("Tesla", "B456DE", "белый", 2022, "Пётр", "INS-002", 75.5)` конструкторы работают с одним объектом:

1. Конструктор `ElectricCar` через `super(...)` передаёт общие данные конструктору `Car`.
2. Конструктор `Car` передаёт их дальше через свой `super(...)`. Конструктор `Vehicle` записывает модель, номер, цвет, год, владельца и страховку.
3. Выполнение возвращается в конструктор `Car`, который записывает в `engineType` значение `"Combustion"`.
4. Выполнение возвращается в конструктор `ElectricCar`, который сохраняет ёмкость `75.5` и записывает в `engineType` итоговое значение `"Electric"`.

`super(...)` вызывает конструктор непосредственного родителя. `this(...)` вызывает другой конструктор того же класса. Например, `RoadBike()` передаёт стандартные параметры полному конструктору `RoadBike` через `this(...)`. Если явного вызова одного из этих конструкторов нет, компилятор добавляет `super()`. Так устроен `Car()`.

### 4. Интерфейс как контракт

Интерфейс задаёт операции, которые можно вызвать через ссылку этого типа. `ElectricVehicle` требует два метода:

```java
public interface ElectricVehicle {
    double getBatteryCapacity();
    void setBatteryCapacity(double batteryCapacity);
}
```

Эти объявления неявно `public abstract`. Поэтому в `ElectricCar` оба метода объявлены `public`. Само значение ёмкости хранится в поле `private double batteryCapacity` класса `ElectricCar`. Другой класс, реализующий тот же интерфейс, может хранить ёмкость своим способом.

В объявлении `class ElectricCar extends Car implements ElectricVehicle` слово `extends` указывает один непосредственный суперкласс, а `implements` подключает интерфейс. Через запятую можно подключить несколько интерфейсов.

| Что нужно описать | Механизм | Пример |
|---|---|---|
| Общие данные и готовые методы семейства классов | Абстрактный класс с полями, конструкторами и методами | `Vehicle` хранит модель и год, даёт методы доступа |
| Возможность, которой могут обладать разные классы | Интерфейс с методами и общими константами | `ElectricVehicle` задаёт доступ к ёмкости батареи |

Интерфейсы Java также допускают методы с телом. `default` даёт реализацию по умолчанию, `static` вызывается через имя интерфейса, а `private` помогает переиспользовать код внутри самого интерфейса. В этой практике используются абстрактные методы. [Спецификация Java, §9.4](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html#jls-9.4)

### 5. Полиморфизм и `toString()`

У одного объекта могут быть ссылки разных типов. Этот пример можно поместить в `main` класса `TestCar`, добавив импорты `vehicles.Vehicle` и `vehicles.ElectricVehicle`:

```java
ElectricCar tesla = new ElectricCar("Tesla", "B456DE", "белый", 2022,
        "Пётр", "INS-002", 75.5);
Vehicle vehicle = tesla;
ElectricVehicle battery = tesla;

battery.setBatteryCapacity(100.0);
System.out.println(vehicle.vehicleType());  // Electric Car
System.out.println(battery.getBatteryCapacity());  // 100.0
System.out.println(vehicle);  // описание Tesla с ёмкостью 100.0
```

Здесь важно различать два шага:

1. **При компиляции** Java проверяет, доступен ли метод через объявленный тип переменной. У типа `Vehicle` есть `vehicleType()`. У типа `ElectricVehicle` есть `getBatteryCapacity()`. Вызов `vehicle.getBatteryCapacity()` не скомпилируется.
2. **При выполнении** Java выбирает переопределённый метод по фактическому типу объекта. Поэтому вызов `vehicle.vehicleType()` использует реализацию `ElectricCar` и возвращает `"Electric Car"`. Это и есть полиморфизм в данном примере.

Для `System.out.println(vehicle)` Java использует строковое представление объекта. Сначала вызывается `ElectricCar.toString()`. В нём `super.toString()` берёт общий текст из `Vehicle` через `Car`, поскольку `Car` наследует этот метод. Внутри `Vehicle.toString()` вызов `vehicleType()` по-прежнему ведёт к методу `ElectricCar`. В конце `ElectricCar.toString()` дописывает ёмкость батареи. В строковом представлении тип транспорта и двигателя показываются по-русски, а `vehicleType()` и `getEngineType()` возвращают значения из задания.

**Перегрузка и переопределение.** `RoadBike()` и `RoadBike(int postHeight)` — перегрузка конструкторов: один класс, разные списки параметров. `Car.vehicleType()` и `ElectricCar.vehicleType()` — переопределение: подкласс даёт своё тело методу с той же сигнатурой.

### 6. Интерфейсы в проекте велосипедов

| Интерфейс | Кто реализует | Что доступно через этот тип |
|---|---|---|
| `BikeParts` | `Bike`, а через него `RoadBike` и `MountainBike` | `printDescription()` |
| `RoadParts` | `RoadBike` | Чтение и изменение ширины шины и высоты подседельного штыря |
| `MountainParts` | `MountainBike` | Чтение и изменение подвески и типа велосипеда |

Строка `String MAKE = "Oracle Cycles";` в `BikeParts` неявно означает `public static final String MAKE = "Oracle Cycles";`. `public` делает константу доступной через имя интерфейса, `static` связывает её с интерфейсом, а `final` запрещает повторное присваивание. Поэтому можно написать `BikeParts.MAKE` и получить название производителя без создания велосипеда. Слово `final` само по себе не делает поле общим. В исходном архиве `private final String make` было полем экземпляра.

В исходном `Bike` метод `printDescription()` был `protected`. Контракт `BikeParts` объявляет его публичным, поэтому реализация в `Bike` и переопределения в обоих подклассах имеют доступ `public`. `RoadBike.printDescription()` вызывает `super.printDescription()` для общей части описания и добавляет данные шоссейного велосипеда.

Стандартный `RoadBike` начинает с высоты 22. Вызов `bike1.setPostHeight("20")` передаёт строку согласно интерфейсу `RoadParts`. Реализация преобразует её через `Integer.parseInt`, записывает число 20 в поле и возвращает его через `getPostHeight()` как `int`.

### 7. Зачем нужны пакеты и как проверить пример

`package vehicles;` указывает, что полное имя класса `Car` — `vehicles.Car`. `TestCar` находится в другом пакете, `app`. Строка `import vehicles.Car;` позволяет писать в нём `Car` вместо полного имени. В части с велосипедами классы и интерфейсы находятся в одном пакете `bikeproject`.

- `private` используется для полей, которые класс скрывает, например `batteryCapacity`.
- `protected` даёт доступ классам того же пакета и подклассам. Поэтому `Car` и `ElectricCar` могут менять унаследованное поле `engineType` напрямую.
- `public` делает методы доступными клиенту из другого пакета. Так `app.TestCar` вызывает `setYear()` и `getBatteryCapacity()`.

При сборке `javac -d out` создаёт дерево скомпилированных классов внутри `out`. Команда `java -cp out app.TestCar` ищет главный класс по полному имени, начиная от корня `out`. Готовые команды для обеих частей есть в [README](README.md#запуск).

### Вероятные вопросы на защите

- **Чем абстрактный класс отличается от интерфейса?** — см. таблицу: у интерфейса нет полей экземпляра и конструктора, члены неявные `public static final` / `public abstract`, реализаций может быть несколько.
- **Почему `printDescription()` стал public?** — метод из интерфейса при реализации нельзя сузить, `protected` больше не компилировался бы.
- **Где используется `TERRAIN` / `terrain`?** — это обязательные по заданию константы интерфейсов; в описании велосипеда печатаются его характеристики, поэтому эти константы остаются частью интерфейсов. Доступ: `MountainBike.TERRAIN`, `RoadParts.terrain`.
- **Почему `engineType` у `ElectricCar` = "Electric", если `Car` ставит "Combustion"?** — сначала отрабатывает `super(...)`, потом тело конструктора `ElectricCar` перезаписывает поле.
- **Почему `MAKE` виден в `Bike` без объявления?** — интерфейс-константа наследуется реализующим классом; полное имя `BikeParts.MAKE`.
- **Можно ли написать `new Vehicle()`?** — нет, класс абстрактный.
- **Что напечатает `println(car)` и откуда берётся подпись «Автомобиль»?** — неявный `toString()` → `vehicleType()` по фактическому типу объекта (полиморфизм); `Vehicle` — только тип переменной (со 2-й практики), в 3-й части 1 переменные объявлены конкретными классами, но dispatch работает так же.
- **Сколько `extends` и `implements` может быть у класса?** — Через `extends` у класса можно явно указать одного родителя. Через `implements` можно указать несколько интерфейсов через запятую.
