# Практика 3 — конспект к защите

## Блок 1. Теория

### Что было в практике 1 (базис)

- Синтаксис Java, primitive-типы (`int`, `double`, `float`...), операторы `+ - * / %`, составные операторы (`+=`, `%=`), приведение типов `(int)1.7`, if / if-else.
- Классы с нуля (без пакетов): поля, методы, `this`, конструкторы (требовалось 3: полный, по умолчанию, «по выбору студента»), создание объектов через `new`, конструктор по умолчанию от компилятора, перегрузка конструкторов (одно имя, разные параметры).
- Константа через `final` у локальной переменной: `final int SMS_PER_METER = 100;` — константа уровня метода.
- Метод `toString()` для вывода полей объекта (в задании был назван `To_String()`), геттеры/сеттеры, метод возраста автомобиля `getAge()`.

### Что было в практике 2 (базис)

- Модификаторы доступа: `private` ограничивает доступ объявляющим классом и вложенными классами в том же внешнем типе. `protected` даёт доступ в том же пакете и в подклассах. Из другого пакета подкласс обращается к унаследованному члену своего экземпляра или экземпляра своего подтипа. Без модификатора доступ ограничен пакетом, а `public` открывает член везде, где доступен его тип.
- Инкапсуляция: поля `private` скрывают представление объекта. Класс определяет, какие операции с состоянием открывать остальному коду.
- Пакеты: `package` перед импортами и объявлениями типов задаёт пакет. Иерархию каталогов обычно строят по имени пакета, а `import` позволяет использовать краткое имя типа.
- Наследование: `extends`, вызов родителя `super(...)`, цепочка классов.
- Полиморфизм: ссылка родителя указывает на объект потомка (`Vehicle car = new Car(...)`), вызывается переопределённый метод потомка.
- **Абстрактный класс уже появлялся** во 2-й практике (part 2): `Vehicle` с полем `engineType` и абстрактным `vehicleType()`. В практике 3 он повторяется как основа, а новое — интерфейсы.

### Новое в практике 3

**1. Абстрактный класс (`abstract class`)**
- Абстрактный класс задаёт общую основу для подклассов. Выражение `new Vehicle()` вызывает ошибку компиляции.
- Может содержать обычные поля, конструкторы (вызываются из потомков через `super`), обычные методы — и абстрактные методы.
- Абстрактный метод объявляется без тела: `public abstract String vehicleType();`
- Конкретный (не абстрактный) потомок **обязан** реализовать все абстрактные методы, иначе не скомпилируется. В работе: `Car` реализует `vehicleType()` → `"Car"`.
- `Vehicle` — абстрактный, `Car` и `ElectricCar` — конкретные. `ElectricCar extends Car`: цепочка из трёх уровней, абстрактный метод «спускается» вниз до первого конкретного класса.

**2. Интерфейс (`interface`)**
- `interface MountainParts { ... }` объявляет отдельный ссылочный тип. Интерфейс в этой работе задаёт контракт из абстрактных методов и общей константы.
- Класс подключает интерфейс ключевым словом **`implements`** (несколько — через запятую). Порядок: сначала `extends`, потом `implements`:
  `public class ElectricCar extends Car implements ElectricVehicle`
  `public class MountainBike extends Bike implements MountainParts`
- **Наследование от класса — одно** (`extends` только один), а **реализовать интерфейсов можно много**. Это способ обойти ограниченность одиночного наследования Java.
- Конкретный класс должен иметь реализацию каждого абстрактного метода. Реализацию можно объявить в самом классе или унаследовать. Так `RoadBike` получает контракт `BikeParts` через `Bike`.
- Ссылка может быть типа интерфейса: `ElectricVehicle ev = new ElectricCar(...);` — полиморфизм через интерфейс (`ev.getBatteryCapacity()` работает, а для `getEngineType()` нужна ссылка типа `Vehicle` или его подкласса).

**3. Члены интерфейса имеют неявные модификаторы**
- Поле интерфейса всегда `public static final` — **константа**, пишется значение сразу: `String MAKE = "Oracle Cycles";` Экземплярского поля у интерфейса быть не может.
- Метод интерфейса без модификаторов `private`, `default` и `static` неявно `public abstract`.
- Отсюда отличие от практики 1: `final int SMS_PER_METER = 100;` — константа одного метода, `private final String make` в исходном `Bike` — константа **одного объекта** (в каждом экземпляре своё значение, но не изменить), а `MAKE` в `BikeParts` — **одна общая константа на весь интерфейс**, доступная как `BikeParts.MAKE` или просто `MAKE` внутри реализующих классов.
- В работе константа `make` из `Bike` удалена и заменена на `MAKE` — единственный источник названия компании.
- Нюанс по заданию: в `RoadParts` константа названа `terrain` со строчной (маленькой) буквы — так буквально в задании. По соглашению константы пишут CAPS (`TERRAIN` в `MountainParts`). На семантику регистр не влияет: `terrain` всё равно `public static final`.

**4. Реализация метода из интерфейса обязана быть `public`**
- В исходном `Bike` метод `printDescription()` был `protected`. При реализации интерфейса его нельзя сузить — пришлось сделать `public` (в `Bike`, `MountainBike`, `RoadBike`). Типичный вопрос на защите: «почему убрали protected».

**5. default- и static-методы интерфейсов (Java 8+, из ссылок README)**
- `default` даёт наследуемую реализацию по умолчанию. Метод класса имеет приоритет, а среди интерфейсов приоритет у более конкретного. `static` вызывается через имя интерфейса. С Java 9 доступны и `private`-методы для внутреннего переиспользования кода интерфейса.
- Если два несвязанных интерфейса дают конфликтующие `default`-методы, класс должен определить свою реализацию. Она может вызвать реализацию прямого суперинтерфейса через `InterfaceName.super.methodName()`.
- В интерфейсах практики объявлены абстрактные методы. Правила для методов с телом описаны в спецификации. [JLS §9.4](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html#jls-9.4)

**6. Абстрактный класс vs интерфейс — шпаргалка**

| | Абстрактный класс | Интерфейс |
|---|---|---|
| Создание объекта | нельзя | нельзя |
| Поля экземпляра | есть | нет (только константы) |
| Конструктор | есть | нет |
| Обычные методы с телом | есть | `default`, `static` и `private` |
| Прямые супертипы | один суперкласс и несколько интерфейсов | несколько суперинтерфейсов через `extends` |
| Когда использовать | общее состояние + поведение потомков | контракт «что умеет», без состояния |

`Vehicle` — абстрактный класс (общие поля-состояние), `ElectricVehicle`/`BikeParts`/`MountainParts`/`RoadParts` — интерфейсы (контракты поведения; состояние `batteryCapacity`, `suspension` и т.д. лежит в классах).

**7. Цепочка конструкторов и порядок инициализации**
- `super(...)` вызывает конструктор родителя. В конструкторах из этой работы присваивания полям потомка идут после вызова `super(...)`. Если явного вызова нет, как в `Car()`, компилятор подставляет `super()`.
- Поэтому у `ElectricCar` сначала `super(...)` → конструктор `Car` ставит `engineType = "Combustion"`, а затем своё тело переставляет `engineType = "Electric"`. Итог — `"Electric"`.
- `engineType` — `protected`: потомки (`Car`, `ElectricCar`) пишут в него напрямую, в том же пакете к полю тоже можно обращаться напрямую.

**8. Полиморфизм и `toString()` (развитие практики 2)**
- `System.out.println(car)` неявно вызывает `car.toString()`.
- `toString()` объявлен в `Vehicle` и вызывает абстрактный `vehicleType()` — в рантайме выполняется переопределение фактического класса, поэтому одна и та же строка кода печатает `Car: ...` или `Electric Car: ...`.
- `ElectricCar` переопределяет `toString()`: `super.toString() + " " + batteryCapacity` — добавляет ёмкость батареи, переиспользуя родительский текст.

### Вероятные вопросы на защите

- **Чем абстрактный класс отличается от интерфейса?** — см. таблицу: у интерфейса нет полей экземпляра и конструктора, члены неявные `public static final` / `public abstract`, реализаций может быть несколько.
- **Почему `printDescription()` стал public?** — метод из интерфейса при реализации нельзя сузить, `protected` больше не компилировался бы.
- **Где используется `TERRAIN` / `terrain`?** — это обязательные по заданию константы интерфейсов; в вывод специально не добавлены, т.к. шаг 7 требует идентичной работы программы. Доступ: `MountainBike.TERRAIN`, `RoadParts.terrain`.
- **Почему `engineType` у `ElectricCar` = "Electric", если `Car` ставит "Combustion"?** — сначала отрабатывает `super(...)`, потом тело конструктора `ElectricCar` перезаписывает поле.
- **Почему `MAKE` виден в `Bike` без объявления?** — интерфейс-константа наследуется реализующим классом; полное имя `BikeParts.MAKE`.
- **Можно ли написать `new Vehicle()`?** — нет, класс абстрактный.
- **Что напечатает `println(car)` и почему там "Car", а не "Vehicle"?** — неявный `toString()` → `vehicleType()` по фактическому типу объекта (полиморфизм); `Vehicle` — только тип переменной (со 2-й практики), в 3-й части 1 переменные объявлены конкретными классами, но dispatch работает так же.
- **Сколько `extends` и `implements` может быть у класса?** — Через `extends` у класса можно явно указать одного родителя. Через `implements` можно указать несколько интерфейсов через запятую.
